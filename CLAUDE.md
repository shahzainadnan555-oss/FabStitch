# FabStitch — project rules

FabStitch is a **B2B wholesale fabric sourcing marketplace**. It connects mills,
converters, dyeing/finishing/printing houses, wholesalers and deadstock sellers
(supply) with garment factories, brands, uniform and workwear makers, home-textile
and technical-textile manufacturers, buying houses and CMT units (demand).

Positioning, in one line: **"Find the right fabric for what you're making — and the
verified suppliers who can produce it at your quantity."**

FabStitch is **not** a fabric catalogue organised by what sellers happen to have.
It is a **discovery marketplace** organised by what buyers are making and the
constraints they are under: quantity, budget, certification, lead time, origin.
FabStitch does the translation from product to specification. Success is measured in
**qualified sourcing conversations**, never in page count or sessions.

## Source of truth, in order

1. Explicit decisions recorded in `docs/DECISIONS.md`.
2. `docs/ARCHITECTURE.md` — the distilled architecture (taxonomy, entities, URLs, page families).
3. The two research PDFs in the repo root — the Blueprint and the Buyer/Keyword/
   Programmatic-SEO Strategy. Treat their concepts, taxonomies and relationships as
   current truth unless a recorded decision supersedes them.

## Current implementation boundary

- This repository is **frontend-only**. There is no current FabStitch backend, API,
  database, authentication service, payment service or WebSocket service.
- Do not add network integration, API environment variables, token/session logic or
  server-backed claims until the user explicitly starts the new backend phase.
- The approved local catalogue under `catalog/` is the current product data source.
- Demo profiles, onboarding and preferences use versioned browser-local state. They
  are not secure authentication or production account storage.
- Buyer, supplier and admin workspaces are honest frontend previews with no fabricated
  operational records or successful submissions.

When the source material does not define something with large architectural
consequences: identify the gap, propose, record the decision in `docs/DECISIONS.md`,
then implement. Do not silently invent it.

## The core chain

Everything — navigation, URLs, filters, page templates, the database — is one
relationship read from different starting points:

```
Buyer → Application → Fabric → Specification → Country → Supplier → Listing
```

Buyers are **never** connected directly to fabrics. They connect through the
application they manufacture. These relationships are **data**, not hardcoded rules
in components. A buyer×fabric page is generated by following the joins; adding a
supplier must improve dozens of pages without anyone editing code.

## Non-negotiable product rules

- **The next step is always obvious.** A buyer must never land on a screen and wonder
  what to click. Entry is possible by fabric, by what they make, by use case, by
  supplier, or by posting an RFQ — all without understanding the taxonomy first.
- **Deep internally, simple externally.** Complexity lives behind the interface.
  Never expose taxonomy, SEO architecture or the data model as navigation.
- **RFQ-first as well as ecommerce-capable.** Samples, swatches, lab dips, custom
  colour/print/finish, negotiated MOQ, tech packs and lead-time confirmation are
  first-class, not add-ons.
- **MOQ and price bands are visible, never behind a signup wall.** Filtering out
  hobbyists early is a feature.
- **Real numbers only.** Counts and facts come from the approved local data source.
  Never invent suppliers, reviews, metrics, certifications or capabilities. An
  unimpressive honest number beats a rounded claim.

## Page and SEO rules

- **Never create a page because a keyword exists.** Keywords live in a planning
  database and are *mapped* onto pages that already deserve to exist.
- A page is indexable only when it passes the full gate in `docs/ARCHITECTURE.md`
  (search intent · listings · suppliers · unique content · uniqueness score · allowed
  combination). Indexability is **computed from data**, never hand-edited, never
  branched in template code.
- **Filter states are query parameters and are not indexable.** Only combinations
  promoted by the gate get a clean canonical path. Letting the filter UI mint
  crawlable URLs is the single most common way a marketplace destroys itself.
- Page count trails listing count. Pages must be able to shrink as well as grow.
- One primary keyword per page. Two pages must never share one.

## Design rules

- The visual language must read as a **serious B2B sourcing company**: custom,
  intentional, precise, credible, industrial/commercial, information-rich where it
  should be, restrained everywhere else.
- Forbidden because they read as AI-generated: giant centred hero, repetitive rounded
  cards, pill soup, glassmorphism, arbitrary gradients, purple/blue SaaS palette,
  decorative oversized type, template three-card sections, fake metrics, generic
  "trusted by" strips, floating decoration, heavy shadows.
- **Design-system first.** Establish the language, then build screens from it. Never
  reinvent a component because one page needs it. Never give a page its own style.
- `DESIGN.md` in the repo root documents **Anthropic's claude.com brand**, not
  FabStitch's. Do not adopt its colours, typefaces or component values as FabStitch's
  design system. See `docs/DECISIONS.md`.
- The installed `.agents/skills/*` design skills contradict each other and mostly
  target marketing pages, not data-dense product UI. Consult them; do not let one
  silently take over the whole product surface.

## Engineering rules

- **Read `node_modules/next/dist/docs/` before writing Next.js code.** This is
  Next.js 16 with Turbopack by default, async `params`/`searchParams`/`cookies()`/
  `headers()`, `proxy.ts` instead of `middleware.ts`, `use cache` + `cacheLife`
  instead of implicit fetch caching, and `revalidateTag(tag, profile)` with two args.
- **Local catalogue data is allowed; fake business logic is not.** Marketplace rules
  never live inside UI components.
- Structured data everywhere. A fabric is never `{name, image, price, description}` —
  it carries composition, construction, GSM and tolerance, width and width type, yarn
  count, stretch, finish, dyeing, certifications, MOQ, price band, lead time, origin,
  sample policy and applications.
- Specifications are **structured and normalised, never free text**. "180 gsm",
  "approx 180" and "175–185" all become an integer plus a tolerance. Store canonical
  units plus the supplier's entered unit; display GSM *and* oz/yd², inches *and* cm,
  price per kg *and* per metre.
- Prefer clear naming, small cohesive modules, explicit types, semantic HTML and
  accessible interactions. Avoid giant components, duplicated UI logic, hidden
  business rules, page-specific hacks, and temporary code presented as architecture.
- Do not delete or rewrite existing code blindly. Report, propose, then change.
